# Yllir entry point

This skill receives every message of the master. It checks the folder, keeps the master's words, and runs exactly one process. Writing processes run in a sub-agent (`yllir:process-runner`) (the instructions of this sub-agent are in `${CLAUDE_PLUGIN_ROOT}/agents/process-runner.md`; if your tool has no named agents, start a sub-agent, tell it to read that file first and follow it exactly), never in this skill. In Codex, always set the model of this sub-agent to GPT-6 Luna in the launch call itself: an omitted model silently becomes the model of the main agent, which is a defect. Run every command from the campaign root (the folder the master opened). Never run a command from another folder.

**Commands.** Run each command exactly as written in this file, as one single command: nothing before it and nothing after it, no `;`, `&&`, `|`, `2>&1`, `echo`, `cat`, `mkdir` or `cd`. Anything added makes the command refused. Every script prints its result and, as its last line, `exit: <code>`: read the exit code from that line (the `exit:` line). Read result files with the Read tool. If a command is refused, run it again exactly as written, with nothing added; if it is refused again, end this skill with `status: FAILED`, reason "permission refused".

## Steps

**Step 1 — Check.** Find the block that starts with `YLLIR SESSION CHECK` in your context. Keep its values: `folder`, `git`, `campaign root`, `saved versions`, `changes not yet saved`, `settings`, `instructions`, `framework version` (with its «campaign made with» part, when there is one), `campaign alignment` (when that line is in the block), `update notice` (the block `YLLIR UPDATE AVAILABLE`, when it is in your context).
- If the block is not in your context: run `node "${CLAUDE_PLUGIN_ROOT}/scripts/session-start.mjs" .` and keep its output the same way.
- Turn record: if the block `YLLIR TURN CHECK` is not in your context (no hook runs in this tool), run `node "${CLAUDE_PLUGIN_ROOT}/scripts/feedback.mjs" record turn .` once per master message. Ignore its result, whatever it is.
- Per-skill record: read `${CLAUDE_PLUGIN_ROOT}/templates/feedback-protocol.md`. On a campaign, start an invocation record for `yllir:yllir` here and keep its id through Step 7b. Follow the protocol for every skill this entry point invokes or reads as a substitute, including linker and canon-research, and pass the parent id in the runner prompt as `FEEDBACK_PARENT:`. Record end status and a local transcript before the final answer. If this runtime does not expose the skill input/output or a feedback command fails, record transcript status `unavailable`; never claim automatic skill-hook coverage. Outside a campaign the log cannot be stored, so continue without claiming a record.
- Output: the values of the block, kept for the next steps.

**Step 2 — Lexicon.** Read `${CLAUDE_PLUGIN_ROOT}/skills/core/yllir/lexicon.md` and read the table.
- From now on, every sentence to the master uses only the words of the lexicon, in the campaign language. The campaign language is `language.main` in `campaign.yaml`. In an empty folder, it is the language the master writes in.
- Output: the lexicon in your context.

**Step 3 — Folder.** Use the `folder` value from Step 1.
- `git: missing`: say in one sentence that the campaign needs a free program called Git to keep its saved versions, and that you will guide the installation if the master wants. Write nothing. Stop.
- `folder: empty`: run the writing process `yllir:new-campaign` as described in Step 6 (TOPIC `none`, HANDOFF `none`). Stop.
- `folder: unfinished` (a campaign was started before and not finished): run `yllir:new-campaign` the same way as for `folder: empty`, and add the line `RESUME: yes` to the runner prompt, after `LANGUAGE:`. Tell the master nothing technical about the earlier attempt: the process gives the master its message. Stop.
- `folder: other`: say in plain words that to bring notes into the campaign, the campaign must exist first. Then ask the one question: should a new campaign be created in an empty folder, so that the material can be brought in right after? Write nothing. Stop.
- `folder: campaign`: continue to Step 4.
- Output: one of the four branches above, with its message.

**Step 4 — Health (campaign only, silent fixes first).**
- **Campaign alignment** (silent). If the block has a line `campaign alignment: needed` or `post-update: needed`: read `${CLAUDE_PLUGIN_ROOT}/skills/core/update/SKILL.md` and follow its Part A exactly, instead of the `instructions` fix below.
- `instructions: missing` or `instructions: changed by hand`, and the block has no `campaign alignment: needed` line: run `node "${CLAUDE_PLUGIN_ROOT}/skills/core/yllir/scripts/generate-instructions.mjs" .`. If the value said `changed by hand`, tell the master in one sentence that a file managed by the assistant was restored, and that their own rules belong in «Your rules».
- `settings: problems: …`: say the fixed sentence of the lexicon for a campaign settings problem, and offer to fix it. Write no campaign content until it is fixed.
- Output: the campaign is aligned (updated, or already up to date), the instructions are up to date, and the settings are valid or the master has been told about the problems.

**Step 5 — Where we left off.** Only if this is the first message of the conversation: run `node "${CLAUDE_PLUGIN_ROOT}/scripts/versions.mjs" list . --limit 3`. Tell the master in at most three short lines what the last saved versions were, using their sentences and dates. If the list is empty, say that nothing has been saved yet. Then handle the message (Step 6). If the first message is a concrete request or a report about a specific document, skip the three-line summary of saved versions and go straight to handling the message. The summary is only for a general opening (a greeting, «cosa abbiamo fatto», or nothing specific).
- Output: at most three lines to the master, or nothing when this is not the first message or when the first message is a concrete request or a report.

**Step 5b — Unlinked mentions (campaign only, every message).** Read the line that starts with `unlinked mentions:` in the block `YLLIR TURN CHECK` in your context. If the block or that line is missing, or the line is `unlinked mentions: none` or `unlinked mentions: unknown`, do nothing here and go to Step 6.

Otherwise, a campaign file was changed outside the write sequence (by hand, by a linked ingest document, or by a migration), and its mentions are not linked yet. Do this:
- (a) Take the file list: the text after `files: ` on that line, without `, and <k> more` at its end if it is there. Keep the names exactly as written and in the same order, joined with commas and no spaces. Call it FILES. SUBJECTS is empty.
- (b) Attempt limit. Read `.campaign/state/linker/attempts.txt` with the Read tool. If the file does not exist, there are no attempts. Each of its lines has the form `<FILES>|<n>`. Find the line whose text before the first `|` is exactly FILES, with the same spelling and order. Its n is the number after the `|`; if there is no such line, n is 0.
  - If n is 3 or more, do nothing in this step: go to Step 6 with the master's message. The master is not told about the linking.
  - Otherwise, before running the linker, write the whole file with the Write tool: keep every other line exactly as it is, and write the line for FILES with n+1 (add it as a new line if it was missing).
- (c) Read `${CLAUDE_PLUGIN_ROOT}/skills/library/linker/SKILL.md` and follow it exactly, with FILES from (a), SUBJECTS empty, and CONTINUE_WITH = "yllir: answer the master". Run it in this skill, not in `yllir:process-runner`. Its result is the file `.campaign/state/linker/report.txt`.
- (d) Read `.campaign/state/linker/report.txt` with the Read tool. If it has lines under `decisions for the master:` and the master's message is a general opening with no concrete request (a greeting, «cosa abbiamo fatto», or nothing specific), say one plain sentence to the master in the campaign language: some mentions could not be linked on their own and wait for the master's choice. When the master's message is a concrete request or a report, say nothing about the linking and keep it silent: the decisions stay pending. Never name files, never show the report, and say nothing else about the linking, even when it failed.
- (e) If the report's status is `DONE`, write the whole attempts file again with the Write tool, with the line for FILES removed and every other line kept. If the status is anything else, or the report is missing, leave the file as it is.
- (f) If the line ends with `, and <k> more`, the rest is handled at the next message: this step runs again then, because the turn check lists the remaining files again. Do not repeat it in this message.
- Then, in the same turn, go on to Step 6 with the master's message. This is what the report's `continue with` line means here.

**Step 6 — Recognise the request** by its meaning, not by keywords. First check Step 7: if the master's message answers the update question, follow Step 7 and skip this step. Otherwise do exactly one of the following.

- **Writing process** (create a campaign in an empty folder; give more setup information to a campaign, see (b); prepare a session; change scenes of a session already prepared but not yet played; record the evening that was played; complete or correct a sheet that already exists (a character, creature, vendor or place); bring in existing material). Changing scenes of a prepared session («cambia il debito dei minatori», «aggiorna le prossime scene») is a request for prepare-session in revise mode, see (b) and (a) below. Bringing in material is recognised by meaning: the master shares photos, scans, PDFs or documents, or says they have existing notes, pages or sheets to bring in or digitise. When files are shared, this is the AUTORUN: start `import` without asking. This entry skill never runs these processes itself. Telling what happened at the table («abbiamo finito», «ieri i giocatori…») is recording the evening; asking for the next session is preparing one. If both are plausible, ask one question. A report about a sheet is an operative request, not a question and not a complaint to answer with words: recognise it by its meaning, for example «La guardia comune ha una scheda praticamente vuota», «la scheda del vecchio minatore è troppo scarna», «manca l'aspetto di Ilde», «nella scheda Ilde è un uomo ma è una donna». Such a report is an AUTORUN, like the import of files: start the process `yllir:complete-sheet` through the runner without asking what the master wants. The only question allowed is the one the process itself asks (for example which sheet, when the name does not identify one). Do not confuse it with a question about the campaign («chi è la guardia comune?» is a question bullet), with recording the evening (what happened at the table), with preparing a session, or with importing files. Those processes are delegated as follows:
  - (a) Choose the topic (campaign folder only). Read the block `YLLIR TURN CHECK` in your context.
    - Same topic as the active one, including an answer to its pending question: reuse it. For `import`, an answer to the question of an open import topic reuses that topic.
    - A different writing request: run `node "${CLAUDE_PLUGIN_ROOT}/skills/core/yllir/scripts/topics.mjs" new . --process <p> --goal "<English one-sentence goal>"`. `<p>` is the process name WITHOUT the `yllir:` prefix: `new-campaign`, `prepare-session`, `after-session`, `complete-sheet`, `import` or `post-update` (never `yllir:prepare-session`). Keep the `id` and `path` of its JSON result. Changing scenes of a prepared session is a different writing request too: use `prepare-session` and a goal such as "Revise scenes of session 2". A report about a sheet uses `complete-sheet` and a goal such as "Complete the sheet of the common guard".
    - A return to an earlier open topic: run `node "${CLAUDE_PLUGIN_ROOT}/skills/core/yllir/scripts/topics.mjs" activate . --id <id>`. If the return is ambiguous, ask the master one question that shows at most three open topics by their goal, in plain words.
    - Quick questions do not change the topic.
    - In an empty folder there are no topics yet: use `TOPIC: none` and `HANDOFF: none`.
    - `yllir:new-campaign` in complete mode (see (b)) uses `TOPIC: none` and `HANDOFF: none`: it is never a topic of its own.
  - (a2) Imagination. Decide the value of IMAGINATION once for each new writing request, and only for PROCESS `yllir:prepare-session`, `yllir:complete-sheet` or `yllir:import`. For the other processes, skip this sub-step and go to (b). Apply these rules in this order; the first rule that applies gives the value, and then go to (b):
    1. The master's message explicitly asks the assistant to invent or choose by itself, for example «inventa tu», «scegli tu», «puoi inventare», «inventale tu», «make it up», «decide yourself» or «you can invent them». The value is `yes`, for this request only. Do not change campaign.yaml and ask nothing. This wins over a setting `false`.
    2. Read `campaign.yaml` in the campaign root with the Read tool and look at the line `allow_model_imagination:`. If its value is `true`, the value is `yes`. If its value is `false`, the value is `no`. Ask nothing.
    3. If the value is `null`, or the line is missing, and the master's message is not an answer to a question the runner asked earlier: ask ONE question with the interactive question tool (AskUserQuestion in Claude Code, request_user_input in Codex), in the campaign language, using the text of the lexicon section «Fixed question about invention». Header: «Fantasia» («Imagination» in English). Question: «Posso inventare dettagli che le fonti non danno (nomi, storia, aspetto, regole)?» («May I invent details the sources do not give (names, history, looks, rules)?» in English). Exactly four options, in this order, label = description = the option text: «Sì», «No», «Sempre sì», «Sempre no» («Yes», «No», «Always yes», «Always no» in English). multiSelect false. Then:
       - «Sì» or «Yes»: the value is `yes`, for this request only.
       - «No»: the value is `no`, for this request only.
       - «Sempre sì» or «Always yes»: run `node "${CLAUDE_PLUGIN_ROOT}/skills/core/yllir/scripts/set-imagination.mjs" . --value true`. Then the value is `yes`.
       - «Sempre no» or «Always no»: run `node "${CLAUDE_PLUGIN_ROOT}/skills/core/yllir/scripts/set-imagination.mjs" . --value false`. Then the value is `no`.
       - If the script ends with a failure, the value is still the one of the answer, for this request only. Say nothing about it.
       - If the question tool is not available or fails: the value is `no`. Ask nothing in text.
    4. If the master's message is the answer to a question the runner asked (the runner's message ended with a question, or you asked it with the question tool in Step 6 (c)): do not decide again and do not ask again. The value is `keep`. Rule 3 does not apply to such an answer.
  - (b) Before launching the runner, if TOPIC is not `none`, run `node "${CLAUDE_PLUGIN_ROOT}/skills/core/yllir/scripts/topics.mjs" check . --id <id>` and use its `changed` list as CHANGED_FILES (`none` when the list is empty). Then launch the sub-agent `yllir:process-runner` in the foreground and wait for its result in the same turn (never with run_in_background). In Codex, set the model of the runner to GPT-6 Luna in the launch call (see the first paragraph of this skill). Never tell the master that you will write later or that work continues in the background: your message is the runner's message for the master, after it has finished. Use exactly these keys, filled in:
    ```text
    CAMPAIGN_ROOT: <absolute path of the campaign root>
    PROCESS: <one of yllir:new-campaign, yllir:prepare-session, yllir:after-session, yllir:complete-sheet, yllir:import or yllir:post-update>
    TOPIC: <topic id, or none>
    HANDOFF: <absolute path of the handoff file, or none>
    CHANGED_FILES: <comma-separated campaign-relative paths from the topic check, or none>
    LANGUAGE: <ISO code of the language the master writes in>
    IMAGINATION: <yes | no | keep>
    FEEDBACK_PARENT: <this entry invocation id>
    MASTER_MESSAGE:
    <the master's message, verbatim; when the master answers a question of the runner, the earlier question followed by the answer>
    ```
    The line `MODE: revise` is optional: add it right after the `LANGUAGE:` line only when the master asks to change scenes of a session already prepared (process `prepare-session`). Otherwise leave it out, which means a new session (`MODE: new` is the same).
    The line `MODE: complete` is also optional, right after the `LANGUAGE:` line, and is used only with PROCESS `yllir:new-campaign`: when the folder is a campaign and the master gives more setup information after the campaign was created, or in a first message after its creation. The setup information is the game system or edition, a folder of shared world material (a source from another campaign), the tone, or more details about the world and the story. Such information is never ignored and never answered with «not available»: launch the runner with `MODE: complete`, `TOPIC: none`, `HANDOFF: none`, `CHANGED_FILES: none`, and the master's message verbatim.
    The line `IMAGINATION: <yes | no | keep>` is optional and goes right after the `LANGUAGE:` line (after the `MODE:` line when there is one), with the value of (a2). Add it only for PROCESS `yllir:prepare-session`, `yllir:complete-sheet` or `yllir:import`. Never add it for `yllir:after-session` or `yllir:new-campaign`.
  - (c) Run `node "${CLAUDE_PLUGIN_ROOT}/skills/core/yllir/scripts/runner-result.mjs" . --file .campaign/state/runner/result.txt --topic <TOPIC or none>`. The script checks the runner's result file, applies the topic change (question or finish) and prints its output. Its output after `message for the master:` is the message, followed by zero or more `ask:` lines (each `ask: <header> | <question> | <options>`), and ends with the line `exit: 0`, which is never sent.
    - Exit 0, without `ask:` lines: send the master exactly the lines after `message for the master:` in its output, and nothing else. Do not add a summary, a status or a file path.
    - Exit 0, with `ask:` lines: do NOT send the message as text. Call the interactive question tool AskUserQuestion once, with one question per `ask:` line: question = the question text, header = the header, options = the options (label = the option text; description = the same option text again, as a short sentence), multiSelect false. The master can also type an answer of their own. The master's answers come back as the master's next message: treat them as an answer to the runner's pending question, and continue from Step 6 (a), building MASTER_MESSAGE as the earlier question followed by the answers, as described in (b). Add nothing else to the question tool's texts.
    - Exit 0, with `ask:` lines, and the question tool is not available or fails: send the master exactly the lines after `message for the master:`, as text, and nothing else.
    - In Codex only: the output has a line model:. If its value does not contain Luna, the runner did not run on the right model. Do not run the process again (its writes are already done). Tell the master nothing about it, and make sure that every later launch in this conversation names GPT-6 Luna explicitly.
    - Exit 1: launch `yllir:process-runner` once more with the same prompt as in (b), plus a line `PROBLEMS:` followed by the `- ` lines the command printed, one per line. In Codex, set the model to GPT-6 Luna, as in the first launch. Then run the same command again. If it exits 1 a second time, say the fixed sentence of the lexicon for an operation that could not be completed.
  - (d) If the runner's final answer is not `result written`, do not send anything: run the command in (c) anyway. A missing or invalid file is a problem for that command, and (c) handles it.

- **Go back** (for example «torna a com'era», «annulla l'ultima modifica»):
  - (a) Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/versions.mjs" list . --limit 10`.
  - (b) Pick the target. «Undo the last change» means the version just before the newest one. A date or a description means the matching version. If two versions are plausible, ask one question and show at most three of them as numbered sentences with dates.
  - (c) Ask one confirmation question: which version you will go back to, and that the later versions stay in the history and can be recovered. If the master's message already contains a clear confirmation (for example «procedi», «confermo», «sì, fallo») and the target from (b) is unambiguous, skip this question and go to (d); in your final message name the version you went back to. Keep the question when the target is ambiguous.
  - (d) After a «yes»: run `node "${CLAUDE_PLUGIN_ROOT}/scripts/versions.mjs" status .`. If `clean` is false, run `node "${CLAUDE_PLUGIN_ROOT}/scripts/versions.mjs" save-manual . --message "<sentence in the campaign language: Changes made by hand before going back>"`.
  - (e) Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/versions.mjs" restore . --to <hash> --message "<sentence in the campaign language: Went back to the version «…»>"`. Add `--paths "<campaign-relative path>"` only if the master named one document. Read the JSON result.
  - (f) Run `node "${CLAUDE_PLUGIN_ROOT}/skills/library/linker/scripts/check-links.mjs" .`. If the exit code is 1, say the fixed sentence of the lexicon for a problem with a link.
  - (g) Tell the master in one sentence what is now as it was, and how to undo this too («go back» again, to the version just saved).

- **Question about the campaign** (for example «chi è…», «dove si trova…»). The answer itself writes nothing; the only change that can come before it in the same turn is the linking of Step 5b, which has already run and which the master is not told about.
  - (a) Read `${CLAUDE_PLUGIN_ROOT}/skills/library/canon-research/SKILL.md` and follow it exactly, with QUESTION = the master's question verbatim, TERMS empty, CONTINUE_WITH = "step b of the question bullet of the entry skill". Run it in this skill, not in `yllir:process-runner`.
  - (b) Read `.campaign/state/research/report.txt` with the Read tool. If it does not exist or its `status:` is `FAILED`, say the fixed sentence of the lexicon for an operation that could not be finished, as it is written there, in the campaign language, and stop this bullet here.
  - (c) Answer the master in plain words, from the report only: the direct answer first, then what it rests on, named by the document titles (never file paths). Say clearly when something is a hypothesis, something a character says, or something the documents do not say. If the report lists homonyms, say which people have the same name and answer for each. If the report has a `not read` list other than `none`, or lists problems, say that the check may be incomplete. Never state as fact a claim the report marks as hypothesis, interpretation or source-claim. Never show the words of the report layout, file paths or status names.

- **Anything else** (change or create documents other than through these processes, tidy up): answer in ONE sentence with the concrete limit that applies to what the master asked, and, in the same sentence or in a second one, the next useful step the master can take, tied to their request. Never list the general features of the assistant in this answer. List them only when the master explicitly asks what the assistant can do: then the list is create a campaign, give a campaign more setup information (system, tone, shared world material, world and story), prepare the next session, modify a session already prepared but not yet played, record the evening, bring in existing notes, photos or documents, complete or correct a card of a character, creature or place, go back to a saved version, and questions about the campaign.

**Step 7 — Update notice.** If your context has a block that starts with `YLLIR UPDATE AVAILABLE`, or your previous message to the master asked whether to update, read `${CLAUDE_PLUGIN_ROOT}/skills/core/update/SKILL.md` and follow its Part B. The master decides: never update without a clear «yes».

**Step 7b — Feedback note (every message, last action).** This is the last thing you do in this message, right before your final answer to the master (also when the answer is a question, when something failed, or when you stopped early). It is never mentioned to the master and never changes the master's message. Skip this step when git is missing (Step 3).
- (a) If the block `YLLIR TURN CHECK` was not in your context at Step 1 (no hook), first run `node "${CLAUDE_PLUGIN_ROOT}/scripts/feedback.mjs" record end .`, adding `--process <name>` when this message ran a writing process (the name without the `yllir:` prefix).
- (b) Always run `node "${CLAUDE_PLUGIN_ROOT}/scripts/feedback.mjs" record note . --outcome <o> --friction <f> --detail "<d>"`. The values:
  - outcome: `ok` = the request was done or answered; `partial` = done in part, or ended with a question for the master after a problem; `blocked` = nothing useful could be done.
  - friction: `none` = no problem; `slow` = it took many steps or a long time for what was asked; `unclear-instruction` = an instruction of a skill was ambiguous or contradictory and you had to guess; `script-error` = a command failed or was refused; `too-many-steps` = the request needed more steps than it should have; `wrong-process` = the first process or branch you picked was not the right one; `other` = anything else.
  - detail: ONE sentence in English, at most 150 characters, about the framework or the instructions (for example which step was slow or unclear). It must NEVER contain the master's words, names, places, plot or any text from the campaign, and no file paths.
- (c) If the command is refused or fails, ignore it: do not retry, do not tell the master, and continue.
- (d) End the `yllir:yllir` invocation with `record skill-end`, including on a question, failure or early stop. Write a local transcript JSON with the master's exact message as `input` and the exact answer you're about to send as `output`, save it first as `.campaign/state/feedback/pending-<id>.json`, and pass it through `--transcript`. Use the matching final status (`ok`, `partial`, `failed`, `blocked` or `question`). If the runtime cannot provide the content, record `--transcript-status unavailable`. This does not change the response to the master.
- Output: nothing for the master.

**Step 8 — Rules.** These apply to every step above.
- Never write or change a campaign document yourself. Every write goes through `yllir:write-sequence`, run by a process. The one exception is Step 5b: the linker, run by this skill as Step 5b says, adds links to campaign documents, and it is the only script-driven writer of links; nothing else in this skill changes a campaign document. The files this skill writes are `.campaign/state/research/answer.json`, only while following canon-research, and, only in Step 5b, the file `.campaign/state/linker/attempts.txt` and the linker's own files in `.campaign/state/linker/`. The feedback commands of Step 1 and Step 7b write `.campaign/state/feedback/events.jsonl` through the script; this skill never edits that file by hand.
- The feedback transcript command reads a temporary JSON file under `.campaign/state/feedback/pending-<id>.json` (written with the Write tool as an explicit exception to the campaign-document rule) and writes `.campaign/state/feedback/transcripts/<id>.json`; these are private local state files and never campaign documents.
- Never run a writing process (`yllir:new-campaign`, `yllir:prepare-session`, `yllir:after-session`, `yllir:complete-sheet`, `yllir:import`, `yllir:post-update`) in this skill: launch `yllir:process-runner` instead.
- Never show internal words, commands, file formats or error codes to the master.
- Write to the master in plain text: no backticks, no code formatting, no file paths, no version codes.
- Ask at most one question at a time (the exceptions are the single AskUserQuestion call of Step 6 (c), which carries the questions of the `ask:` lines, and the single question call of Step 6 (a2), about invention).
- Never say something is done without the result of the command that did it.
- Keep maintenance in the background: answer the concrete request or report first and only that. Older saved versions, ambiguous links, mentions waiting for a choice and similar housekeeping are not part of the answer unless the master asks about them.
- When a command or check fails, say only the matching fixed sentence of the lexicon, or the closest one. Never explain permissions, commands, file formats or why it failed. Never write the words YAML, JSON, Claude, command, permission, script or a file name. The only exception is the sentence of Step 3 for `git: missing`, which names Git.
- The feedback commands (Step 1 and Step 7b) are the one exception to the rule of the Commands paragraph about refused commands: if one is refused or fails, ignore it and never end with `status: FAILED` because of it. Never speak to the master about feedback or about this record.

## Progress messages

While a process runs, send the master at most ONE short progress message, at the start, saying what you are doing in plain words. Do not send repeated «still checking» messages, do not poll a running process for status more often than once every two minutes, and never say it is almost finished unless the process has already reported it is on its last step. When the work was long, the final message states only the result.

## Examples

Correct, writing request (the master, in an empty folder, writes «crea una campagna»): no topic is needed. Launch `yllir:process-runner` with `PROCESS: yllir:new-campaign`, `TOPIC: none`, `HANDOFF: none` and the master's message verbatim. The runner's result file passes the runner-result command (exit 0); send the master only the text after its `message for the master:` line, in plain Italian.

Wrong, writing request: running `yllir:new-campaign` (or writing the draft and calling `yllir:write-sequence`) directly in this skill. The entry skill never runs a writing process itself.

Correct, go back (the first message of an Italian campaign is «annulla l'ultima cosa che hai fatto»): the three-line summary of the last saved versions, then one confirmation question in plain Italian, naming the version to go back to.

Wrong, go back: «Ho eseguito git revert sul commit a1b2c3». It uses technical words, and it gives no confirmation question before acting.

Correct, `folder: other` (the master writes «ho qui delle note di una partita»): one message that says the notes must go into a campaign that exists first, and asks whether the master wants a new campaign created in an empty folder, so the notes can be brought in right after. Nothing is written.

Wrong, `folder: other`: creating a folder called `Notes/` to hold the master's files before asking.

Correct, complete mode (the campaign was created in this folder, and the master's next message is «il tono è cupo, la storia parla di una città mineraria»): launch `yllir:process-runner` with `PROCESS: yllir:new-campaign`, `MODE: complete`, `TOPIC: none`, `HANDOFF: none`, `CHANGED_FILES: none` and the master's message verbatim. Then send the master the message of the runner's result, or ask the question of its `ask:` lines with the question tool.

Wrong, complete mode: answering «questa informazione non è disponibile» or ignoring the tone and the story, or opening a topic for them. Setup information is never refused, and it uses no topic.

Correct, change to a session already played (the master, in an Italian campaign, asks to change the plot of a session already played): one sentence that played sessions are not changed, and that the change can go into the next session. Nothing else.

Wrong, change to a session already played: «Questa funzione non è disponibile. Posso: creare una campagna, …» followed by the full list of features.

Correct, report about a sheet (Italian campaign, the master writes «La guardia comune ha una scheda praticamente vuota»): launch `yllir:process-runner` with `PROCESS: yllir:complete-sheet`, a new topic (goal "Complete the sheet of the common guard") and the master's message verbatim. Send only the runner's message.

Wrong, report about a sheet: answering «Posso aiutarti con altre cose, ecco cosa posso fare…», or asking «Che cosa vuoi che faccia?».

Correct, invention question (Italian campaign whose setting `allow_model_imagination` is `null`; the master writes «scrivi la scena della taverna», with no request to invent): one question with the question tool, Header «Fantasia», the four options «Sì», «No», «Sempre sì», «Sempre no». If the master picks «Sempre sì», run the set-imagination command with `--value true`, then launch `yllir:process-runner` with `PROCESS: yllir:prepare-session`, the topic, the line `IMAGINATION: yes` right after `LANGUAGE:`, and the master's message verbatim.

Wrong, invention question: asking the four-option question when the master already wrote «inventale tu» (that is a request, the value is `yes`, and nothing is asked), or asking it again when the master's message answers a question the runner asked (the value is `keep`, and nothing is asked).
